Data point for this design, from measuring #361's branch under headless Claude Code (Opus) on a repo with 109 markdown files and a six-task doc-question bank, same repo rules in every arm.

Indexing markdown as heading and section nodes changed nothing by itself: 24 cells, 0 explore calls, calls and correctness identical to Grep-then-Read, which already answers a doc question in 1 to 3 calls. What moved the number was the shape of the answer. With the server instructions corrected to say docs are indexed, and explore rendering the matched file's best sections first and whole (top three sections, idf-weighted line hits, 8k cap per file, no code blast radius unless a code file rendered), three rounds of 12 fresh cells each gave:

| Criterion                                       | Round 1 | Round 2 | Round 3 |
| ----------------------------------------------- | ------- | ------- | ------- |
| Correct                                         | 12 / 12 | 12 / 12 | 12 / 12 |
| Tool calls, median (Grep-then-Read baseline: 4) | 1       | 1       | 1       |
| Explore adopted                                 | 10 / 12 | 11 / 12 | 10 / 12 |
| No Grep or Read after explore                   | 8 / 12  | 9 / 12  | 9 / 12  |

Every explore call across the 36 cells picked the right file and section; the residual is the model reading one prompt as being about its own scheduling tools, and grepping a file the prompt names. Cost per cell $0.30 against $0.54.

So for the opt-in design here: the doc→symbol `references` edges are the graph-coherent part, but the win the model actually takes is a doc hit that returns the section body first, with its code context optional. Three things a shared index needs regardless of the node shape, found while porting to 1.6.0: markdown must skip the "generated by" header check; markdown section text in the shared FTS table matches into code queries unless filtered; and the budget tiers keyed on `fileCount` flip when markdown crosses a breakpoint. Details and the port: comment on #361 and bompus/codegraph@26c0190.
